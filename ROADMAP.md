# InclusiveTalk — Product Roadmap

## Vision

Образовательная платформа делающая обучение в смешанных классах (слышащие + глухие/слабослышащие студенты) доступным без переводчика жестового языка в каждой комнате.

Целевой рынок: учебные заведения СНГ. ~500K студентов с нарушениями слуха в регионе. Острый дефицит сурдопереводчиков (1 на 500+ глухих в Казахстане).

## Текущее состояние (Декабрь 2026)

**MVP в продакшне:** [inclusivetalk.vercel.app](https://inclusivetalk.vercel.app)

Работает:
- Живые субтитры лекции на 3 языках (русский, казахский, английский)
- Коды комнат, до N студентов на урок
- Обратная связь от студента: 5 готовых сигналов + свободный текстовый вопрос
- Идентификация студентов по имени
- Список подключённых студентов в реальном времени

Технологический стек:
- Frontend: Next.js 16, React 19, TypeScript, Tailwind CSS, deployed on Vercel
- Backend: Node.js, Fastify, WebSocket, deployed on Railway
- Speech recognition: Web Speech API (Google)
- Real-time communication: WebSocket
- Repository: GitHub (private)

## Фаза 2 — Месяцы 1-3 после раунда

**ИИ-ассистент для студента**
- Кликабельные термины в субтитрах — студент кликает на непонятное слово, ИИ объясняет простыми словами
- ИИ-генерация контекстных вопросов на основе темы урока
- Гард-промпт: ИИ не выдаёт готовые решения задач, только объяснения концепций

**Расширение функционала урока**
- Личные ответы преподавателя конкретному студенту
- Сохранение транскрипта урока для просмотра позже
- Статистика участия студента (время, количество вопросов)
- Уведомления преподавателю (звуковые + визуальные)

**Качество распознавания речи**
- Переход с Web Speech API на OpenAI Whisper для лучшего качества казахского
- Автоопределение языка для смешанной речи (типично для Казахстана)

### Биллинг и SaaS-модель
- Интеграция платёжной системы (Stripe для международных, Kaspi/Halyk для Казахстана)
- Подписочная модель для учебных заведений с месячной/годовой оплатой
- Автоматическая блокировка доступа при неуплате (Suspended статус)
- Email-уведомления о статусе оплаты
- Free tier для небольших классов (до N студентов)

### Личные кабинеты
- Регистрация преподавателей с верификацией от учебного заведения
- Сохранение истории уроков и транскриптов
- Статистика участия по студентам
- Управление группами/классами
- Студент остаётся доступным по коду без регистрации (анонимный вход)

### Локализация интерфейса платформы
- Полный UI на казахском, русском, английском
- Автоопределение языка из настроек браузера
- Возможность смены языка интерфейса в настройках профиля
- Локализация писем-уведомлений

## Фаза 2 — Доступ для учебных заведений (модель «Колледж → Преподаватели»)

> Статус: продумано на словах 16.06.2026. В код НЕ берём, пока нет подписанного договора с УЗ.
> Принцип: студенты остаются «лёгкими» (вход по коду, без регистрации) — не добавляем барьеры.

### Модель доступа (бизнес-логика)

**Три уровня:**
1. **Учебное заведение (организация)** — клиент по договору. Имеет: название,
   срок действия доступа, лимит N преподавательских доступов.
2. **Преподаватель** — привязан к колледжу, логинится, создаёт комнаты, ведёт занятие.
   Сейчас зародыш этого уровня = teacher token.
3. **Студент** — БЕЗ логина. Вход по коду комнаты + имя. Барьеров не добавляем.

**Ключевое правило:** комната привязана к ПРЕПОДАВАТЕЛЮ и его текущему занятию,
НЕ к предмету.
- Причина: один препод за день ведёт разные группы; одна группа ходит к разным
  преподам. Привязка к предмету запутает, привязка к преподу — чисто.
- Формула: 1 колледж → N преподавательских доступов → каждый препод создаёт свои
  комнаты → студенты входят по коду.

**Единица продажи/выдачи доступа = преподавательский доступ (N преподавателей).**
Не студенты, не комнаты. Причина: студенты не регистрируются; число комнат
естественно ограничено числом преподов; считать и выставлять счёт проще по преподам.

### Масштаб пилота (для расчёта нагрузки)
- ~5 преподавателей разных дисциплин (химия, биология, основы программирования и т.д.)
- группы по ~10 студентов
- параллельно ~3-5 одновременных комнат, в каждой до ~10-15 студентов
- Вывод: текущая инфра на Railway это держит без проблем. Масштабирование НЕ страх.

### Что НЕ делаем сейчас (граница против scope creep)
- На первый пилот хватает: teacher token + комнаты по коду + ручная выдача доступов
  преподавателям (Модель Б — ручное распределение). Новая авторизация НЕ нужна.
- Договора ещё нет → кода ещё нет.

### Что входит в Фазу 2 (когда появится подписанный договор + счёт)
- Сущность «Аккаунт колледжа» (название, срок, лимит N преподавателей)
- Лимит преподавательских доступов на уровне колледжа
- Админ-доступ для меня: видеть, кто из колледжа сколько комнат провёл
- Модель А (самораспределение: админ колледжа сам раздаёт доступы преподам) —
  переезжает сюда из «ручной выдачи», когда колледжей станет несколько

## Фаза 2 — Качество распознавания доменных терминов (контекст предмета)

> Статус: идея 17.06.2026. Большая тема, 3 подсистемы. НЕ трогаем как «быструю правку».
> Обсудить системно, возможно с тех-трекером ITM Lab. Инвесторы спросят про это.

**Проблема:** на предметном уроке (химия, биология) Web Speech API путает
термины — напр. химический термин распознаётся как «футбол». Это портит и
субтитры студенту, и AI-генерацию вопросов (gpt-4o-mini уходит не в ту тему).

**Три части (разной сложности):**
1. Контекст предмета для распознавания — чтобы система «знала» тему урока.
   ⚠ Ограничение: Web Speech API почти не даёт управлять словарём. Возможно
   потребует смены движка распознавания — серьёзное архитектурное решение.
2. Защита AI-генерации вопросов от мусорного слова (фильтр/контекст перед gpt-4o-mini).
3. Редактирование/удаление субтитра:
   - учитель вручную правит/удаляет распознанное слово на своём экране  ← дешевле всего
   - либо автоочистка через ИИ

**С чего начинать, когда возьмёмся:** пункт 3 (ручная правка учителем) —
не требует менять движок, работает с текущей архитектурой, сразу полезно.
